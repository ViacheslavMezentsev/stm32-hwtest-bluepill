# DDTT в Renode/GDB и GitHub Pages

[English](DDTT_RENODE.en.md). Этот маршрут не обращается к платам и не использует
аппаратную карту: `hil/ddtt-renode.template.json`, сценарий `tools/renode_gdb_checks.py`.

## Что означает раскраска

Десять связей на семи строках `main.cpp`/`app.cpp`: вход main, исходное состояние setup_done,
порядок setup → board::init → uart::init → post::run → loop, завершение setup, ожидаемый
PostAdcTimeout и UART-баннер выбранной платы. Это утверждения о данной модели, а не
подтверждение электрических характеристик или полного покрытия функций.

В Renode 1.17 моделируются ядро, память, SysTick и USART1. ADC — RAM-заглушка,
DMA не моделируется. Поэтому строка UART `POST: ... FAIL` ожидаема и не означает отказ
сценария. Проверка `model ADC timeout` утверждает именно этот ограниченный исход.
Нельзя объединять карту emulator с hardware или приписывать ей аппаратные проверки.

Runner собирает новый Debug ELF F103CB в уникальной папке build, запускает свой Renode,
подключает GDB с Python, останавливается на функциях и читает состояние. После завершения
он закрывает свои процессы. Входы сборки, модель, сценарий, карта и генератор сверяются
с полным Git SHA до и после опыта. Входы должны быть закоммичены; несвязанные изменения
документов и `.clang-format` не мешают. Новые исходники сначала добавляют в Git.
Во время опыта файлы не редактируют; это снимки до/после, не криптографическая аттестация.

## Локальный запуск

```powershell
python tools/renode_ddtt.py --revision (git rev-parse HEAD) --gdb "$HOME/xpack-arm-none-eabi-gcc-14.2.1-1.1/bin/arm-none-eabi-gdb-py3.exe" --annotations
```

Renode ищется по `RENODE_BINARY`, PATH или стандартному пути Windows; можно указать
`--renode`. Тулчейн сборки — `ARM_TOOLCHAIN_ROOT` или штатный поиск CMake.
Пределы: configure/build по 120 с, готовность Renode 30 с, GDB 60 с, ответ remote 10 с.
Это короткий автоматический тест, не сеанс ручной отладки.

Открыть `build/ddtt-renode-pages/index.html`: выбрать файл, нажать окрашенную строку,
посмотреть утверждения и ссылки на сценарий/исходник точного SHA. Ссылки начнут работать
на GitHub после push этой ревизии. Темы: тёмная/светлая/авто. Для переноса копируют пять
файлов этой папки, не всю папку build. LCOV/Cobertura содержат относительные пути и
булевы DA; UNKNOWN исключается из числовой карты. При прерывании/ERROR вся попытка
неполная, зелёные промежуточные отметки не публикуются. Явный FAIL даёт 0 и красную строку.
Сырые result/log остаются в отдельной `build/renode-ddtt-*`; последующие попытки их не затирают.

## CI и аннотации

Обычный CI выполняет этот маршрут в задании `build (f103cb-debug)`. В сводке Actions
появятся итог и артефакт **ddtt-renode-pages**. Скачать ZIP, распаковать, открыть index.html.
**ddtt-renode-diagnostics** содержит отдельные журналы для диагностики, не для Pages.

`notice` сообщает подтверждение, `error` — ложное утверждение, `warning` — неизвестный
исход. Аннотации привязаны к исходному файлу/строке в проверенной ревизии и видны в
интерфейсе Checks/Actions; это не постоянная зелёная полоса в обычном просмотре репозитория.
Полная интерактивная раскраска находится в HTML. Workflow использует документированные
[workflow commands](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands).
Сам `error` не заменяет exit code: runner отдельно завершает FAIL/ERROR ненулевым кодом.

## Как потом открыть Pages

Публикация по push выключена. Workflow только подготовлен, никаких настроек GitHub
и развёртываний агент не выполняет.

1. После CI и land открыть **Settings → Pages → Build and deployment → Source: GitHub Actions**.
2. Открыть **Actions → CI → Run workflow**, выбрать **main**, включить **publish_pages**.
3. Этот запуск заново собирает и проверяет прошивку. Задание `pages` ждёт успешные format
   и все build-задания, публикует только переносимый эмуляторный комплект.
4. После успеха открыть ссылку окружения **github-pages** в задании `pages` или **Visit site**
   в Settings → Pages. При стандартном адресе это
   `https://ViacheslavMezentsev.github.io/stm32-hwtest-bluepill/`.
5. Выбрать файл в отчёте и нажать строку. Для обновления повторить ручной запуск на main.

До первого успешного deploy сайт отсутствует. Обычный CI обновляет артефакт, но не сайт:
проверяйте SHA в заголовке Pages. Новый deploy заменяет предыдущий сайт репозитория целиком;
он не добавляет эмуляторный раздел к существующему аппаратному сайту. Если Pages уже занят
другим содержимым, сначала согласуйте структуру сайта. Аппаратный отчёт этой задачей не публикуется.
См. [настройку custom workflow](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).
