# Нейтральные маршруты: время, стоимость и внешний захват

Используй по задаче, не запускай все примеры автоматически. Эти приёмы уточняют
[TECH-022/024/026](../../../docs/ru/TESTING_TECHNIQUES.md#tech-022), не расширяют API.
Сначала найди checkout модуля той же ревизии. Команды ниже выполняются **из его корня**;
скопированному навыку нужны также соседние навыки и исходники tests из этого checkout.
Не считай путь от установленного SKILL.md корнем проекта потребителя.

## Выбор маршрута и критерий приёмки

| Задача | Пример | Что принять |
| --- | --- | --- |
| Порог, wrap времени, повтор после отказа | [logical-time](../../../tests/logical-time/README.md) | Четыре host-варианта; Renode 20 ожидаемых исходов: 15 PASS, 5 точных FAIL, два повтора исправления |
| Разность счётчика и расходы наблюдения | [counter-cost](../../../tests/counter-cost/README.md) | Четыре host-варианта; Renode 20 исходов: 17 PASS, 3 точных FAIL; пять полных журналов транспорта |
| Пригодность внешней записи | [external-capture](../../../tests/external-capture/README.md) | Host 19 исходов анализа: 2 PASS, 2 FAIL, 15 UNKNOWN; отдельные исходы сценария/захвата/очистки |

Это эталоны комплектных примеров, не обязательные количества для проекта потребителя.
Их проверили на Windows/Linux; текущий запуск подтверждай свежими артефактами.
External-capture — host-модель с отдельным процессом, **не @case, не Renode и не плата**.

## Команды без платы

```sh
python tests/logical-time/run.py --host-only
python tests/counter-cost/run.py --host-only
python tests/external-capture/run.py
```

Для первых двух после host используй штатный Renode-маршрут:

```sh
python tests/logical-time/run.py --toolchain <ARM-GCC-root> --renode <Renode-executable>
python tests/counter-cost/run.py --toolchain <ARM-GCC-root> --renode <Renode-executable>
```

Значения в угловых скобках замени установленными путями; готовые PowerShell/Linux
примеры — в README. Нужны host g++, Python 3.11+, ARM GCC/GDB-Python и Renode 1.17.
External-capture требует только Python. Docker на Windows: исходники и сборки в одном
volume по [локальному CI](../../../docs/guides/ru/local-ci.md), не запуск через bind mount NTFS.

Каждая кампания создаёт новый каталог build/<example>/<id>. Сохрани summary, исходные
result/records либо fixture-файлы, хеши входов и журналы. Summary PASS означает
**совпадение ожидаемой матрицы**, а не превращение намеренных FAIL в PASS.
В Renode обязательны capture, проверенный ELF, восстановление POD и cleanup VERIFIED.
Отсутствие данных/иная проверка FAIL/ошибка очистки — остановка разбора, не повод
ослабить ожидание или увеличить таймаут. Следующий исправленный повтор должен пройти
при тех же входах; аппаратное подтверждение требует отдельного согласования.

## Logical-time: не скрывать остаток старого состояния

Задай порог −1/порог/+1, пропуск момента опроса, wrap и повтор после отказа **без reset**.
Время передаётся числом в функцию: sleep ПК или await wait не продвигают его.
Для uint32_t нужны допустимый интервал и условие отсутствия пропущенного полного оборота.
Отвергнутый start должен сохранить объект; отказ приложения (return 0) — check, не refused.

Правильно: call один раз, проверить outcome/return_state, затем return_value; в async def
использовать await. Неправильно: сравнить весь словарь call с числом, спрятать вызов
в read/evaluate, повторить call ради чтения значения или сделать reset перед retry.
POD сохраняется по размеру ELF, восстанавливается в finally с обратным чтением даже
при FAIL. Этот способ не восстанавливает DMA/периферию, callbacks и внешние эффекты.

## Counter-cost: сначала пригодность, затем число

Независимо обоснуй верхнюю границу прироста **строго меньше** полного оборота, полноту
выборок и неизменность эпохи. Не вычисляй эту границу из проверяемой пары отсчётов.
valid=0 означает неизвестность; delta=0 при этом не измеренный ноль.

Пустой контроль и полное возмущение различаются: в модели 3 тика внутри интервала,
6 тиков всего. Стоимость 7 тиков на единицу работы задана, а не измерена на MCU.
Не переносить этот baseline на DWT. Для MCU нужны MMIO/SVD, доступность счётчика,
halt/sleep, конфигурация/восстановление и независимая оценка расходов/погрешности.

Реальный perf_counter_ns вокруг call измеряет запрос ПК/GDB/транспорта. Сохраняются
шесть выборок, первая заранее исключена как прогрев; анализ пересчитывает медиану
и максимум остальных пяти. Это описательная статистика, не WCET и не скорость MCU.
Нет записи, неверная область/прогрев или несогласованные числа — отказ анализа,
при этом исходный вердикт сценария сохраняется. Не выбирай только удобные выборки.

## External-capture: отдельный вердикт после drain

Сначала READY, затем окно, после него drain/EOF и ожидание своего процесса. Exit 0
источника не доказывает полноту: сверяй end-маркер, seq, канал, единицы, run/revision.
Синхронное ожидание pipe/subprocess выполняется внешним host-координатором, **не в
главном потоке GDB и не внутри async-сценария**. wait/halt не выполняют drain.

Сверяй весь интервал погрешности временной привязки: внутри допуска — PASS, целиком
вне — FAIL, пересечение — UNKNOWN. Опоры/offset этого примера заданы моделью; нельзя
объявлять их измеренной синхронизацией стенда или подгонять по желаемому результату.
Полная пригодная запись с противоречием даёт FAIL анализа при сохранённом PASS сценария;
неполная/несопоставимая — UNKNOWN. При отсутствии READY сценарий NOT_RUN, не SKIP.

Повторный анализ существующего опыта не запускает источник и не переписывает сценарий:

```sh
python tests/external-capture/analysis.py build/external-capture/<campaign>/<case>
```

Exit 0/1/2 здесь означает PASS/FAIL/UNKNOWN, а не исход команды всей кампании.
Проверяются хеши, если имеется sha256.json; это контроль изменений, не аутентификация.
Схемы scenario/capture/analysis JSON — учебные, не штатный result/records модуля.
Не подавать их напрямую экспортёру DDTT и не обещать импорт rosbag/MCAP: адаптеры ещё
не реализованы. Для потребителя сначала определи контракт источника и его преобразование.

## Перенос выводов в DDTT и отчёт

Сохраняй отдельно исходный сценарий, полноту захвата, анализ, cleanup и область среды.
Привязывай только конкретные проверенные утверждения: UNKNOWN блокирует зависимые,
но не независимые свидетельства. Не меняй исходный PASS/FAIL и не окрашивай все строки.
Для отчёта явно называй модельные тики, время транспорта и подставные временные опоры;
не выдавай host-fixture за аппаратную квалификацию. Применимость карты определяет
автор сценария; эти примеры не добавляют автоматический импорт в coverage/report.
